# 画像コードメソッドと物理演算の追加設計

2026年10月5日 JST。設計案。実装・依存インストール・公開・GitHubへのpushは行っていない。

## 結論

既存GLSLメソッドを維持し、別種の「JavaScript画像メソッド」を追加する。Three.jsで画像の面・破片・立体を描画し、GSAPで時間演出、Troika Textで同じシーン内の文字、Rapierで衝突・重力・反発を扱う。作成したメソッドは「＋追加」から名前付きブロックとして保存・再利用・ファイル交換できる。

歌詞コードの隔離実行基盤を参考に、画像専用の実行経路を増設する。1枚モードとシーケンスには同じAPI・同じメソッド一覧・同じフレーム生成器を使う。今回は設計までとし、既存作品やユーザーの制作データを変更しない。

## 現行構造と再利用範囲

| 対象 | 確認した実装 | 設計への影響 |
| --- | --- | --- |
| GLSL | `custom-method.js`で頂点シェーダーへ差し込み。`method-registry.js`は29組込＋cm系GLSLを想定 | GLSLの番号、8,000文字制限、検査、素材との対応を維持 |
| 画像変形 | `motion.js`で崩れ座標、立体の目標座標、A/Bミックスを計算 | 別シーンのJSをGLSL関数の代わりに挿すだけでは動かない |
| 歌詞コード | `code-motion-runtime.js`、`code-motion-worker-entry.js`、`code-motion-layer.js` | iframe＋Worker、期限超過終了、フォント、古い応答破棄を参考にする |
| 歌詞の描画 | WorkerからImageBitmapを返す前面合成 | そのまま画像メソッドへ使うと、背景を置き換えられず深度も共有できない |
| カメラと演出 | 両モードの本体で計算。`effects.js`のボケは深度テクスチャを使用 | 画像Workerへ同じカメラ状態を渡す。ボケはWorker内で処理するか未対応を表示 |
| シーケンス書き出し | `sequence.js`は指定時刻の歌詞フレームをawaitしてWebCodecsへ送る | 画像フレームの完了待ちも同じ位置へ追加できる |
| 1枚モード書き出し | `app.js`はMediaRecorderと実時間録画 | 重い物理計算に向かない。新メソッドには共通のコマ単位書き出しが必要 |
| 保存形式 | `.unfold`はv1〜3、`.unfoldmethod`はv1 | JSを旧GLSL欄へ格納しない。新形式を区別する |

1枚モードの画像寸法は元画像のアスペクトから算出し、シーケンスは出力アスペクトに合わせた面を使う。どちらも高さは `min(3.65, 5.25/aspect)` 系であり、x±2.6・y±1.5を常に固定として扱わない。

## 利用者の操作

1. 画像または◆変形を選び、メソッド一覧の「＋追加」を押す。
2. 「GLSLで作る」「JavaScriptで作る」を選ぶ。既存の編集画面と保存済みGLSLは継続利用する。
3. JavaScript側でサンプル、画像、コード、プレビューを表示。通常の再生・時刻スライダーに加え、物理用の重力・反発・破片数などを出す。
4. プレビューして名前を付けて追加。1枚モードにもシーケンスにも同じブロックが出る。
5. 「コードをコピー」と「メソッドファイルを書き出す／読み込む」を用意する。GLSL側のuserMethodコピーは維持する。

物理モードではamountと時刻を分ける。amountを下げることを「物理世界を負の時間で進める」と解釈しない。「逆再生で戻る」「配置を整えて戻る」をサンプル側で選べるようにする。

## 推奨する描画構成

旧メソッドは従来の本体レンダラー、新メソッドは専用の画像シーンWorkerへ分岐する。新方式は画像区間の描画を担当し、単なる歌詞の上乗せとしては扱わない。

本体から送るのは対象画像A/Bのローカルデコード結果、画像面の寸法、クリップ時刻・長さ、seed、見た目の設定、カメラ行列、許可されたフォントなど。そのフレームに不要な音楽やプロジェクト全体は送らない。画像は外部送信しない。

Worker内では画像片とTroikaの文字を同じThree.jsシーンで描く。このシーン内では文字の前後関係や、Rapierの当たり判定を設定できる。ただし文字形状そのものの精密な当たり判定は自動生成せず、最初は箱などの代理形状にする。

完成したImageBitmapを本体が受け取り、既存のMV歌詞レイヤーをその前に合成する。画像面の再投影はせず、完成フレームとして合成する。カメラや色変換を二重に適用しない。背景色、透過、SRGB、premultiplied alpha、上下方向、ピクセル比を共通の入出力契約で固定する。

**合成境界の制限：** 本体側のGLSL／GLBと別Worker側の文字は、ImageBitmapだけでは深度を共有しない。既存MV歌詞の「立体の裏への回り込み」はこの追加だけでは実現しない。画像コード内で一緒に描く文字と画像片は前後関係を持てる。この2つをUIで混同させない。

既存の画面効果は「Worker内の3D材質・深度効果」と「合成後の画面効果」に分けて一度だけ適用する。共通化できた効果から有効にし、未移植のガラス・深度ボケなどを効いているように表示しない。

## 提案APIと時間の契約

新APIは仮称 `imageMethod/v1`。既存歌詞APIのピクセル座標とは別に、画像面の実際のワールド寸法を基準にする。

- `api.THREE`、`api.gsap`、`api.Text`：描画・演出・文字。Troikaは文字が必要な場合だけ使う。
- `api.scene`、`api.root`：編集可能な画像シーンと、ホスト管理の回転・位置を受けるグループ。描画器の直接操作は渡さない。
- `api.images.a/b`、`api.size`：ホストで読み込んだ画像テクスチャとワールド寸法。
- `api.createImagePlane()`、`api.createImageTiles()`：UVを保つ画像面・分割片の補助関数。
- `api.createText()`：選択済みローカルフォントと色を使う補助関数。
- `api.seed`、`api.random`、`api.params`：再現可能な乱数と、保存対象の演出設定。
- `api.physics`：ホストが所有するRapier World、物体生成・力・イベント・描画との対応づけ。Worldのstep・時刻・復元は実行基盤が管理する。
- `api.RAPIER`：高度な設定のために公開する場合も、描画更新から勝手にstepしない契約を設ける。JSの自由度が高いため規約だけで再現性を保証したとは扱わず、検証済みメソッドを区別する。

作者が返すオブジェクトは、停止状態のGSAP timeline、`update(frame)`、必要なら固定ステップ用の`beforeStep(step)`と`afterStep(step)`、`dispose()`を持つ案。frameにはclipTime、progress、amount、form、phase、direction、imageMixを渡す。progressは0〜1、amountは既存のdistort×strengthに合わせる。outputWidth/outputHeightは描画専用で、物理のサイズ・重力・破片数を出力解像度から変えない。

`update`は絶対時刻から表示を求める。`position += ...`の累積、Date.now、Math.random、requestAnimationFrame依存は再現性を壊すため、標準サンプルでは使わない。GSAP timelineはpausedで時刻を指定する。物理の衝撃をGSAPの通過コールバックへ置くとシーク時に二重発火しうるため、物理イベントは固定step番号に結び付ける。既存歌詞Workerの `seek(time,false)` は画像物理へそのまま流用しない。

## Rapierの巻き戻しと保存動画

固定刻みを初期案1/60秒とし、整数step番号で進める。30fps・60fpsの出力でも同じ物理軌跡を参照する。刻み間の表示は位置補間とQuaternion補間を使い、物理状態へ補間結果を書き戻さない。

同じ初期状態から、同じ順序で物体・衝撃・パラメータを処理する。Rapierのバージョン、seed、初期配置、重力、固定刻み、コードとパラメータを保存する。公式資料の決定性は同一バージョン・同じ初期値／追加順序が条件で、任意のユーザーJSやGPUの完全一致まで保証するものではない。

戻るときは負のdtを使わず、初期状態か直前のチェックポイントへ復元し、必要なstepまで順に再計算する。長い区間は位置・回転のベイクも選べるようにする。world.takeSnapshotだけでは作者のJS変数・乱数・イベント済み状態・GSAP状態は保存されないため、それらも別に復元する。復元したWorldに対して古いRigidBodyオブジェクトを使わず、安定した論理IDから再取得する。未対応の作者状態がある場合は初期化から再演算する。

「逆再生で戻る」は保存済み軌跡を逆順参照する。「配置を整えて戻る」は物理結果から平面へ補間する演出であり、自然落下の物理計算だけで元絵へ戻るとは説明しない。

キャッシュキーにはソース、API／依存版、seed、画像・設定、シーン寸法、物理設定、区間長を含める。表示解像度だけの変更では物理を変えない。カメラ変更で物理が変わるモードは最初は設けない。

共通フレーム生成は `await prepareFrame(time, output)` → 描画／合成 → エンコード。プレビューは最新リクエストを優先し、古い応答を破棄。シーク中は必要なら準備表示を出す。書き出しはコマを省略せず、途中開始でも区間先頭からの物理状態を復元する。

シーケンスのWebCodecs／MP4Writerを共通化し、新メソッドの1枚モードにも使用する。既存MediaRecorder経路は旧メソッド用に保持できるが、新物理方式の正式な高品質出力はコマ単位とする。非対応ブラウザでは理由を示し、動画ができたと誤認させない。

## 既存機能との接続と初期範囲

- GLSLのみの作品・GLSL同士のmethod2ミックスは従来経路を維持する。
- JS同士／JSとGLSLの組合せに、頂点座標の直接ミックスを約束しない。最初は明示的な映像クロスフェードで扱い、両モードに同じ制限を表示する。
- 最初のJS方式は「画像A → 物理／コード演出 → 画像B」、1枚モードはB=A。区間端は既存の平面画像描画へ正確につなぐ。amountだけを試すプレビューの0も原画にする。立体化中のstrength=0は従来同様、formを無視して平面化しない。
- 現行の回転方向・移動・ズームは本体が計算し、Workerの管理グループ／カメラへ適用する。自由コードのカメラ上書きは初期版では公開せず、二重適用を防ぐ。
- 既存の「立体化する形」へ連続変形する部分は別の接続工程。共通グリッドの目標頂点を受け取れる補助関数から対応する。任意のJSトポロジーから全GLB形状への自動モーフは初期版に含めない。対応前は新メソッドの形選択を「なし」に限定し、既存GLSLでの形選択は維持する。
- Troika文字は新画像シーン内で画像片と衝突・前後移動できる。現行の歌詞MVのタイミング編集や描画方式を自動移行しない。

初期サンプル案は「タイルが落ちて跳ねる」「爆発して元へ戻る」「画像片と文字がぶつかる」の3つ。Rapier 0.21の公式資料には布・ロープ・柔らかい物体もあるため拡張候補にするが、第一段階は剛体に絞る。布、紙の折れ、液体、本格的モーフィングがRapier追加だけで完成するとは扱わない。

## 保存と実行の境界

`.unfoldmethod` v2へ型タグを追加し、既存vertex形式はGLSLとして読めるようにする。新JSには別ID系、engine／apiVersion／runtimeVersion、source、パラメータ定義、標準値、seed・物理設定、対応機能を保存する。現状のcm判定やresolveKeyは型を見て分岐させ、新IDが勝手にくしゃくしゃへ置換されないようにする。

新方式を含むプロジェクトだけ`.unfold` v4とし、旧v1〜3は現行読込を維持する。GLSLだけのファイルは従来形式で出力可能にする。未対応版では明確に停止し、誤った映像へ黙って置換しない。メソッド配布ファイルには画像・曲・フォント本体を含めず、作品ファイルでは従来の素材同梱規則を維持する。

読み込んだコードは静的検証だけでは実行しない。明示プレビュー・有効化と、コード内容に結び付いた確認状態を使う。ネットワーク・DOM・ストレージへアクセスしない既存の隔離方針を継承し、依存JS/WASMはローカル同梱、ホスト取得してWorkerへ渡す。Rapier compatはWASMを内包する方式を候補とし、CSPでのWASMコンパイルを実際のブラウザで確認する。既存unsafe-evalの条件を確認し、不要なネットワーク許可を追加しない。

元のbridgeは画像の入力転送を想定していないので、ImageBitmap／ArrayBufferのホスト→iframe→Worker転送と所有権・close／破棄処理を追加する。期限超過・キャンセル・再選択時の世代番号、古い応答破棄、Rapier world.free、Troika／Threeのdisposeを必須とする。Worker終了はUI停止への対策であり、GPUやメモリ枯渇まで完全に隔離すると断言しない。

性能の初期目安は256剛体、上限候補1024、軽いコライダー、画像片のインスタンス描画。これは未測定の予算案。通常の6,400粒を全部剛体に置き換えない。メモリ・WASM・GPU・復元時間を測って上限を決める。歌詞Workerと画像Workerが同時に動く場合も測る。キャッシュはLRU・容量上限・破棄ルールを持ち、プレビュー品質を落としても物理軌跡は変えない。

## 実装の順序と受入条件

1. **画像だけの技術検証**：専用Worker、元画像表示、UV付き分割、カメラ受け渡し、Troika文字、GSAP。開始／終了とamount=0の原画、透過画像、縦横比、色を比較する。
2. **物理と時間**：Rapier初期化、床とタイル、固定step、seed、再初期化／復元、逆シーク、取消。時刻0→2→1→2と、最初から2へ飛ぶ場合の位置・回転を比較する。
3. **両モードとファイル**：一覧・＋追加・エディタ・保存・再読込・Undo/Redo・未確認コード・異なる型の混在。旧GLSLと旧作品の挙動を回帰確認する。
4. **動画出力**：両モードで同じフレーム生成器を使い、720p／1080p、30／60fps、途中書き出し、音声、MP4のデコード、キャンセル後の状態復元を検証する。解像度によって物理結果が変わらないことも確認する。
5. **立体との接続と拡張**：グリッド対応の立体目標、既存効果、GLBの対応範囲を増やす。剛体版の品質を確認してから布／柔体を検証する。

無限ループ、異常値、過剰生成、画像差替え途中、期限超過、再選択、キャッシュ失効、未対応ブラウザをテストする。比較は物理の数値と、同一環境の描画差分を分け、異なるGPUでPNG完全一致までは要求しない。

現時点では実装・実機テストは未実施。主な要検証点はWASMと既存隔離環境、画像転送、色／深度効果、物理の復元速度、1枚モードのコマ単位書き出し。昨夜の304件成功は現行版の記録で、この新方式の検証結果ではない。
